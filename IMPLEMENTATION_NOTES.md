# Implementation Notes

## Delivery status

This is the first runnable foundation of V1. It includes a Compose stack, versioned PostgreSQL/pgvector schema, FastAPI event/watch/collection surfaces, an incremental RSS collector with per-feed audit records and URL/exact-content deduplication, provenance-bearing reported claims, a provider boundary for Ollama, citation-validated event Q&A, and a Next.js event desk with India, history, changes, contradiction, related-event, and watch-indicator sections.

Feature 1 now adds deterministic structured entity extraction to every newly inserted document, including exact-content duplicate documents. `backend/app/entities.py` applies curated canonical names and aliases to title and excerpt text without an LLM; it stores exact character offsets separately for each field. Canonical records are reused by `(canonical_name,type)`, aliases are persisted in `entity_aliases`, and occurrences are persisted in `document_entity_mentions`. `GET /documents/{document_id}/entities` exposes the stored resolution and original mention text. Reprocessing replaces a document's mention rows transactionally and reuses existing canonical rows.

The initial dictionary covers a deliberately bounded set of countries, organizations, military units, weapons/systems, aircraft, vessels, locations, facilities, and economic entities. `Washington` and generic force phrases such as `Iranian forces` remain explicitly unresolved. This is surface-form extraction, not general NER: it misses names outside the curated alias list, does not infer actor/target roles, and does not turn plain generic references such as “regional allies” into entities. It also does not establish whether any reported statement is true.

Verification for Feature 1: 14 backend unit/regression tests pass; Python compile and `git diff --check` pass; `docker compose config -q` passes. Migration 004 applied to the current PostgreSQL volume; health is green; a temporary persisted fixture was inspected through the new API, processed twice, and removed. Direct database inspection found 3 canonical entities, 11 aliases, 0 remaining fixture mentions, and no duplicate mention keys. CPU-only extraction of a representative 2-field document fixture took 0.032 s / 100 documents, 0.152 s / 500, and 0.302 s / 1,000 on this host; these timings exclude database writes and network/feed collection.

Feature 2 adds a replaceable `ClaimExtractor` interface and a bounded `DeterministicClaimExtractor` in `backend/app/claims.py`. The collector invokes it after entity mentions are persisted and an incident is available; it also processes exact-content duplicate documents attached to an existing incident. It recognizes the project's nine claim types using sentence, predicate, attribution, negation, quantity, time, and location rules. It stores the original statement, normalized JSON attributes, affirmed/negated polarity, epistemic status, attribution chain, intent label, extraction method/confidence, document/source provenance, exact title/excerpt spans, and canonical entity links. The new `GET /documents/{document_id}/claims` route exposes these fields. Claim truth confidence remains `UNVERIFIED` and is distinct from extraction confidence.

Duplicate collapse is intentionally conservative: candidates collapse only when their deterministic normalized predicate, polarity, epistemic status, intent, and attribution signatures match. Each distinct source span is retained. Fire/launch wording and other lexical paraphrases remain separate unless the signatures match; there is no embedding or semantic merge. Weekday and relative time expressions are retained without an invented date. Explicit ISO dates, full month dates, and UTC clock expressions are normalized only to their expressed precision. Qualitative quantities such as “dozens” retain an unknown numeric value.

It produced 8 extracted claims, exact source spans, and actor/object/target entity links; no duplicate span keys were found. The rollback-only integration test verified repeated extraction reuses claims/spans and links entities. Feature 3 adds deterministic evidence reference extraction and provenance in `backend/app/evidence.py`. It extends the existing `evidence` and `claim_evidence` models rather than creating a second evidence store. Evidence references retain exact title/excerpt spans, reporting document/source, directness, attribution, provider/reference IDs when explicit, extraction metadata, and source-specific claim relationships. Evidence types reuse the existing database taxonomy (`SATELLITE_IMAGERY`, `GEOSPATIAL_DATA`, `VIDEO`, `PHOTOGRAPH`, `FLIGHT_TRACKING`, `SHIP_TRACKING`, `RADAR_DATA`, `OPEN_SOURCE_ANALYSIS`, and the other existing enum values).

## Feature 4 — Structured document-to-incident resolution

Migration `007_incident_resolution.sql` adds normalized incident identity fields, indexes for actor/target/action/time/location retrieval, evidence identity links, and one auditable resolution record per document. `backend/app/incident_resolution.py` defines the replaceable `IncidentCandidateRetriever` and `IncidentResolver` interfaces with deterministic implementations. It reads only persisted structured claim roles, canonical entity IDs, normalized event-time precision, explicit evidence identity, quantity, consequence, response, and related entities. It does not use headline similarity, embeddings, an LLM, claim truth confidence, or event-thread resolution.

The resolver requires several independent identity signals and compatible/nearby event time or shared explicit evidence plus other structured support. Exact actor and target conflicts and major exact-time differences block a merge. Quantity and evidence differences are retained as conflicts; quantity mismatch alone never splits an incident, and evidence identity alone never merges one. Equal plausible candidates remain ambiguous. Resolution state, categorical match strength, selected signals, conflicts, candidate audit and limitations are inspectable through `GET /documents/{document_id}/resolution` and `GET /incidents/{incident_id}`. Match strength describes identity evidence and is not truth probability.

The collector stages entities, claims and evidence on a provisional incident to satisfy existing foreign keys, resolves the resulting structured fingerprint, then attaches document and document-specific claim rows to the selected incident. Each report retains separate claim IDs/source spans and source-specific evidence-document links even when an explicit evidence ID is reused. Exact content hashes remain an explicit deduplication path. Resolution exceptions retain the staged incident and record `RESOLUTION_FAILED`. Multiple distinct occurrence predicates are marked `REVIEW_REQUIRED` rather than silently merged; the current one-incident-per-document field cannot split such an article. Existing incidents are not silently backfilled/re-resolved. `python -m app.backfill_incident_fingerprints` is a dry-run index-only command; `--apply` adds structured fingerprints from stored claims/evidence without changing assignments.

Feature 4 verification: all 50 backend tests passed in Docker; this included six live PostgreSQL/API integration tests covering Feature 1–3 regression and Feature 4 grouping, claim separation, evidence provenance, API inspection, idempotency and multi-occurrence review. The controlled 50 reports clustered into five expected groups with no cross-event merges or extra splits. Database-backed fixture: Reuters + AP joined one incident, while the next-day attack stayed separate; claims remained document-specific and one explicit image identity stayed shared with two document links. API debug routes returned stored fingerprints and resolution audits. CPU-only matching over the 50 reports took 0.001498 seconds in the final recorded run; this excludes SQL retrieval and network. All 001–007 migrations also passed on a temporary clean PostgreSQL database. The index-only backfill populated 14 existing incidents and did not change any document assignment; existing resolution audit rows are created when each new document is processed. Docker API, database and dashboard health were checked.

## Feature 5 — Incident-to-Event Thread resolution

Migration `008_event_thread_resolution.sql` adds conservative thread status/timing fields, per-incident structured context, indexed aggregate thread profiles, explicit incident-to-incident relationships, and assignment audits. `backend/app/event_thread_resolution.py` implements replaceable candidate-retriever and resolver protocols. The indexed retriever is capped at 50 threads. The resolver uses canonical participant and domain continuity, a bounded 30-day temporal window, and explicit source-language response/causal cues; location and time alone never assign a thread. Multiple eligible candidates are marked `AMBIGUOUS`; incomplete plausible matches are `REVIEW_REQUIRED`. Each incident remains a distinct record with one primary thread assignment. Supported relationship edges are persisted separately and idempotently.

Newly ingested incidents pass through Feature 4 first and Feature 5 second. Deterministic titles are derived from canonical country/organization names and a bounded context domain; unknown titles use a stable thread UUID prefix. Thread profiles are rebuilt from member incident fingerprints/entities; the resolver does not infer a concluded state from inactivity. Resolver failures are isolated in a savepoint, preserve the staged incident and prior intelligence, and receive a `RESOLUTION_FAILED` audit. Existing records can be previewed with `python -m app.backfill_event_threads`; the default mode is rollback-only, and `--apply` persists assignments.

Debug APIs: `GET /incidents/{incident_id}/event-thread`, `GET /event-threads/{event_thread_id}`, `/timeline`, and `/relationships`. Feature 5 does not merge incidents or add contradiction/truth confidence, importance, India relevance, historical analysis, embeddings, RAG, LLM decisions, forecasting, alerts, or dashboard redesign.

Migration 006 adds document/evidence references, evidence spans, evidence/source provenance, evidence lineage, source-specific claim/evidence relations, explicit identity keys, extraction metadata, and indexes. An exact external evidence ID or URL can reuse one evidence row across documents. Identical descriptions without an explicit identity remain separate. Publisher citations resolve to a specific prior document only when that document is attached to the same evidence identity; otherwise the publisher citation is retained without guessing an article. `GET /documents/{document_id}/evidence` exposes the evidence, spans, directness, attribution, metadata, source references, lineage, and claim relationships.

## Feature 6 — Contradiction, confidence, importance, and material change (in progress)

Migration `009_feature6_intelligence.sql` extends the existing `contradictions`, `claims`, `incidents`, and `event_threads` structures and adds the idempotent `material_changes` and `feature6_failures` tables. `backend/app/feature6.py` groups at most 1,000 claims per thread, builds structural candidate buckets, and caps candidates at 20 prior claims per claim and 5,000 pairs per thread pass. Rule-based assessments persist `CONTRADICTS`, `COMPATIBLE`, `INCONCLUSIVE`, or `NOT_COMPARABLE`, scope, reason, and method; no model or embedding makes a final decision. Exact numeric conflict checks require the remaining statement scope to match; lower-bound/range/approximate values do not become exact conflicts. Location changes require matching residual proposition and role; time values compare only at equal precision, with start/end kept distinct. Intent conflicts require the same explicitly reported objective and opposite polarity. Status checks currently recognize the narrow destroyed-versus-operational pair.

Claim confidence is categorical and recomputed from linked evidence relations, provenance groups only when an independence key/group/origin source is explicit, directness, evidence strength, contradictions, latest publication time, and source tier context. Publisher tier and recency are shown as context and do not independently assert truth. HIGH requires multiple identified groups, direct evidence, and at least one evidence item marked HIGH/STRONG; missing independence stays unknown. Importance remains separate and combines named impact dimensions plus linked incident count. The deterministic phrase rules are a starting point and require broader fixture coverage before operational use.

Material changes are stored with dedupe keys for newly detected contradictions, a country/organization actor newly entering an existing thread, and a HIGH/CRITICAL importance rise accompanied by a bounded explicit military, economic, diplomatic, or humanitarian change phrase. Repeated processing updates one contradiction per normalized pair/type and deduplicates material transitions. Collector calls Feature 6 inside a savepoint after Feature 4/5, and records failures in `feature6_failures` without discarding source records. New routes expose claim contradictions/confidence, incident/thread importance, and thread material changes; the dashboard adds compact assessment sections.

Source registry changes enable Firstpost World's official RSS and Reuters-attributed Google News RSS. The Reuters entry is explicitly an AGGREGATOR, not an official Reuters feed. WION, Republic World, Reddit, and a Firstpost Vantage filtered feed were attempted; inaccessible or stale endpoints are registered disabled with their verification notes. Source/configuration details are in `backend/app/default_feeds.py`.

**Feature 6 is verified complete.** The implementation hardening covered all 8 contradiction categories (OCCURRENCE, ATTRIBUTION, QUANTITATIVE, LOCATION, TIME, INTENT, STATUS, CONSEQUENCE), wire-copy source independence chains with lineage resolution, 5-level categorical confidence with explainable basis, 5-dimensional importance independent of confidence, deduplicated material changes (SIGNIFICANT_CONTRADICTION, NEW_MAJOR_ACTOR, GEOGRAPHIC_EXPANSION, MILITARY_ESCALATION, ECONOMIC_CONSEQUENCE, DIPLOMATIC_SHIFT, HUMANITARIAN_CONSEQUENCE), savepoint failure isolation via `feature6_failures`, and strict multi-pass idempotency across 95 passing regression tests. Live dashboard verification in the browser confirmed proper display of importance dimensions, material changes timeline, contradictions, and provenance-linked claims.

## Deliberate constraints

- Feature 4 resolves independently reported documents to incidents; Feature 5 assigns those distinct incidents to a persistent Event Thread. Exact-content duplicates retain the same incident and its existing thread. Differently titled articles can join an incident only when Feature 4's structured matching rules support it.
- Current ingestion records an unverified reported headline claim and runs bounded entity, claim, and evidence extraction. Evidence identity is conservative and provenance supports independence analysis later; it does not resolve contradictions or assess claim truth/confidence.
- Feature 6 rules are conservative and limited to structured fields. Inconclusive pairs remain unresolved; candidate grouping can miss lexical paraphrases.
- Historical tables and India exposure tables are present, but historical research/reuse and causal impact investigation are not implemented yet. No history or economic observations are seeded.
- Vector storage is provisioned, but embeddings are not currently generated or queried. No vector threshold is used for identity.
- Existing `event_updates` records still represent collection discoveries; Feature 6 material-change records are separate. Watch toggling exists, but alert delivery is not implemented.
- Collection is in-process and starts immediately with the API. On-demand/periodic failures are isolated per feed; there is no separate worker process or backoff queue.
- Initial feed URLs are configuration examples and may be unavailable or change. Individual errors appear at `/collection/runs`.

## Manual steps for the user

1. Install/start Docker Desktop, copy `.env.example` to `.env`, and set a local password before first launch.
2. Optionally install and run Ollama and pull the configured model to enable event Q&A.
3. Review feed availability, source terms, and excerpt retention before adding/depending on sources.
4. Authorize Tailscale on the user's devices if private remote access is wanted; the app does not configure account access.
